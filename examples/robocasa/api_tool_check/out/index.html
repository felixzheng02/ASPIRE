RoboCasa CaP API tool check

What this is. Every one of the 31 public tools the ASPIRE agent is handed for the robocasa embodiment, called through the same namespace a generated program gets (CapApi.register_tools(ToolRegistry(public_extension_allowlist=ROBOCASA_PUBLIC_TOOL_NAMES))), with its input and output drawn so the answer can be judged by eye. One task (PickPlaceCounterToStove), one seed (101), instruction "Pick the fish from the plate and place it in the pan." Nothing was fixed; problems are reported where they were found.

Reading this page. Each tool below has a table of the calls made (input, result, whether it behaved) followed by the figures. "Behaved" means the call did what the API reference says it does — a correctly refused bad input counts as behaving. Rotating GIFs are 3D views; the videos are the simulator's own cameras during each motion.

Cross-check through the real sandbox. api_tool_check.py (the catalog written as a generated program) was also run under cap-harness run on the same task and seed: program_ok=True, termination_reason=program_completed, 269 ticks, and all 31 tools reachable from inside runtime.py's sandbox (out/sandbox/). Note that that script marks a tool "ok" when the call returns — it reports move_synchronized and plan_synchronized_motion as ok by design ("a typed failure is still a successful probe of this tool"). It proves reachability; the figures below are what test behaviour.

The short version

Perception, kinematics and motion control are sound. The calibration round trip is exact to 1e-13 px; two cameras with different intrinsics and extrinsics place the same object within 1–5 mm of each other in robot0_link0; the reported end-effector origin projects exactly between the two fingertips visible in the wrist camera. IK solutions, when driven, land 3.7–5.9 mm and under 0.6° from the pose they were solved for. move_to_pose holds under 6 mm on every axis tested, move_to_joints and go_home converge to under 0.01 rad, all five plan_motion strategies return paths, and the grippers, the step loop and the error paths behave as documented.

Grasping does not work end to end, and three smaller things are wrong.

Problems found

  1. generate_grasps is non-deterministic and often empty. Asking three times in a row for the same mask of the same frame, with max_candidates 1, 8 and 30, returned 0 / 1 / 0 candidates on the fish, 1 / 8 / 1 on the plate seen as "pan", and 1 / 0 / 0 on the plate. A separate retry loop on an identical fish mask returned 0, 0, 0, 2 on four consecutive calls. So the cap is honoured but the pool behind it is random between 0 and 8 for unchanged input, and the most common answer for a small object is NO_GRASP. Scores, when candidates exist, are 0.16–0.22. A program cannot rely on this call returning anything, and retrying is not obviously wrong.
  2. The grasp pipeline reaches the candidate but picks nothing up. Driven end to end, the arm reached the best candidate to within 8.6 mm, the jaw then closed to 0.011 — near-zero, which on this binary gripper means it met no object — and a 12 cm lift left the fish's centroid where it was (+0.000 m). The frame handling is right (see next item); the candidate itself straddles the edge of the fish. See generate_grasps → "Driving the best candidate".
  3. A grasp pose is not a move_to_pose target, and nothing says so. The returned pose sits exactly 0.1034 m behind its own reported contact_point along its local +Z: it is a gripper base (panda_hand) pose, while solve_ik and move_to_pose take a gripper0_right_eef pose and internally subtract another 0.1 m. Passing a candidate straight through therefore puts the hand 10 cm short of the object. Both readings are reachable, so solve_ik returns ok for either and nothing flags the mistake. Correcting it (eef = pose + 0.1 · z, rotation × Rz(−90°)) put the hand within 9 mm of the candidate — the overlay figure shows the two coinciding. Also note width_m = 0.08 and approach_distance_m = 0.0 are provider constants, not predictions.
  4. move_synchronized can never succeed on this embodiment. plan_synchronized_motion happily returns a SynchronizedTrajectory, but RobocasaAdapter.execute_trajectory accepts only a Trajectory, so the call comes back INVALID_REQUEST: invalid trajectory: trajectory must be a Trajectory. The planning half of the pair works and the execution half cannot.
  5. robocasa.get_controller_metadata()["joint_limits"] does not describe the arm. It publishes low = [0, 0, 0, 0, -2.8973, -1.7628, -2.8973], high = [0, 0, 0, 0.34, 2.8973, 1.7628, 2.8973]. Four of the seven measured joint positions fall outside their own published range — joint 3 reads −0.503 against a published [0.0, 0.34]. The simulator builds this from model.jnt_range[:7], the first seven joints of the whole MuJoCo model, which on PandaOmron are base/torso joints followed by arm joints 1–3; the real limits of arm joints 4–7 are never published. A program that clamped its targets to these numbers would drive the first four joints to zero.
  6. segment_text has no presence test. Asking agentview for "sink" — nothing of the sort is in frame — returns the plate at score 0.72 with ok=True. "pan" (there is one, but on the far side of the stove and out of this camera's view) returns the same plate box at 0.035. The call always returns up to five ranked masks and never an empty result, so a score is the only signal, and a high score is not evidence the thing exists.
  7. The arm cannot be raised from its spawn pose. Holding orientation, solve_ik solves for +1 and +2 cm of +z and fails from 3 cm upward (it reaches 12 cm forward). That is a workspace edge, not a defect, but it is sharp, undocumented, and the IK_FAILED error carries an empty details, so the residual that caused the rejection is not visible to the caller.
  8. Smaller notes. select_grasp(..., "top_down") returned None for every candidate on this scene (they all approach from the side), so a program that only uses that strategy gets nothing. mask_to_point_cloud's documented default target_frame="robot_base" always raises here, since this adapter's base frame is robot0_link0. robocasa.plan_approach_pose(distance_m=0.7) returns (0, 0, yaw) when the object is nearer than distance_m — a silent no-op — and the yaw it suggests makes the spawn footprint report blocked. One navigate_to_pose yaw command achieved 0.279 of 0.30 rad but also drifted the base 3 cm and was reported as not converged.

Confirmed working as documented: forward base motion from spawn is blocked by the counter and reports it (5.5 cm of 30 cm); set_gripper(0.5) is refused before a tick is spent; step strips the reward; a stale trajectory is refused with STALE_PLAN; robocasa.base_pose_is_free agrees with the counter point cloud pushed into world through robocasa.get_base_pose on 100% of sampled points.
